## 2. 本書の目的

本書は、StockPilotに求められる非機能要件を定義することを目的とする。

機能要件定義書で定義した機能を適切な品質で提供するため、可用性、性能、運用性、保守性、セキュリティ、ユーザビリティおよび開発品質などに関する要件を明確にする。

また、需要予測機能を提供する機械学習システムについて、再現性、モデル管理および予測処理の安定性に関する品質要件を定義する。

本書で定義した非機能要件は、後続の基本設計、詳細設計、実装、テストおよび運用設計の基礎とする。

なお、本書は架空の顧客企業を想定した個人開発プロジェクトの要件定義書であり、実際の企業とのサービス品質保証契約に基づくものではない。

## 3. 非機能要件の定義方針

### 3.1 基本方針

非機能要件の定義にあたっては、以下の方針を採用する。

- 業務要件および機能要件に基づいて品質要件を定義する。
- 各非機能要件に一意の識別子を付与する。
- 各非機能要件の対象リリースおよび優先度を明確にする。
- 可能な限り客観的に検証可能な受入基準を定義する。
- 数値による品質目標には測定条件を定義する。
- 個人開発の規模および運用コストを考慮する。
- 無料利用可能なインフラサービスの制約を考慮する。
- 業務データの整合性およびセキュリティを重視する。
- 機能要件と重複する仕様は関連要件への参照によって管理する。
- 実装方式に依存しない要件定義を原則とする。
- 後続工程で決定する事項は未決事項として管理する。

### 3.2 識別子

| 識別子      | 名称                           | 管理対象                   |
| ----------- | ------------------------------ | -------------------------- |
| NFC-XXX     | Non-Functional Category        | 非機能要件の分類           |
| NFR-XXX     | Non-Functional Requirement     | 個別非機能要件             |
| NFR-TBD-XXX | Non-Functional Requirement TBD | 非機能要件に関する未決事項 |

識別子の連番は3桁とする。

一度確定した識別子は原則として変更しない。

要件を追加する場合は新しい識別子を付与し、既存の識別子を再利用しない。

要件を廃止する場合は、その理由および変更履歴を記録する。

関連する業務要件、業務ルール、業務フロー、機能要件、共通機能要件および分析・評価要件については、各ドキュメントで定義された既存の識別子を使用する。

### 3.3 優先度

非機能要件の優先度は、機能要件定義書と同様にMoSCoW法を参考に分類する。

| 優先度 | 意味   | 定義                                           |
| ------ | ------ | ---------------------------------------------- |
| Must   | 必須   | 対象リリースの成立に必要な要件                 |
| Should | 重要   | 重要であるが、合理的な理由により延期できる要件 |
| Could  | 任意   | 開発状況に応じて対応を検討する要件             |
| Won't  | 対象外 | 対象リリースでは対応しない要件                 |

Mustに分類された要件は、対象リリースまでに受入基準を満たす必要がある。

ShouldおよびCouldに分類された要件を延期する場合は、その理由および影響を記録する。

Mustに分類された要件の変更または延期が必要となった場合は、正式な要件変更として管理する。

### 3.4 個別非機能要件の記述項目

各非機能要件は、原則として以下の項目によって構成する。

| 項目         | 内容                                 |
| ------------ | ------------------------------------ |
| 要件ID       | 非機能要件の一意の識別子             |
| 要件名       | 非機能要件の名称                     |
| 要件分類     | 対応するNFC-ID                       |
| 要件内容     | システムに求められる品質または条件   |
| 定義理由     | 当該要件を定義する理由               |
| 優先度       | Must / Should / Could                |
| 対象リリース | v0.1.0 / v1.0.0                      |
| 受入基準     | 要件を満たしていることを判断する基準 |
| 確認方法     | テスト、測定、レビューなどの確認方法 |
| 関連要件     | 対応する既存の要件ID                 |

該当する項目が存在しない場合は、その旨を記載する。

### 3.5 品質目標および受入基準

非機能要件は、可能な限り客観的に確認できる内容とする。

性能などの数値目標については、必要に応じて以下の条件を定義する。

- 測定対象
- 測定環境
- 対象データ量
- 同時利用者数
- 測定方法
- 合格基準
- 測定対象外となる条件

要件定義時点の品質目標は、実測結果ではない。

実際の測定結果は、後続のテスト工程および運用確認において記録する。

品質目標を満たせない場合は、その原因および影響を確認し、改善または要件変更によって対応する。

### 3.6 トレーサビリティ

非機能要件は、関連する業務要件、業務ルール、機能要件、共通機能要件および分析・評価要件との対応関係を保持する。

特定の機能に限定されない非機能要件については、システム全体に適用する共通要件として位置付ける。

詳細な対応関係は、後続の要件トレーサビリティマトリクスで管理する。

### 3.7 要件変更の管理

非機能要件の追加、変更または廃止を行う場合は、以下の内容を確認する。

- 変更理由
- 関連する業務要件および機能要件
- システム品質への影響
- 対象リリースへの影響
- 設計、実装およびテストへの影響
- 運用コストへの影響

変更内容はGitHub Issue、Pull Requestおよびドキュメントの改訂履歴によって管理する。

## 4. 非機能要件の前提条件

### 4.1 システムの利用規模

| 項目                 | 前提                       |
| -------------------- | -------------------------- |
| 対象店舗数           | 1店舗                      |
| 想定商品数           | 約500商品                  |
| 利用形態             | Webブラウザによる利用      |
| 表示言語             | 日本語                     |
| 通貨                 | 日本円（JPY）              |
| 業務上のタイムゾーン | Asia/Tokyo                 |
| 需要予測単位         | 商品別・日別               |
| 需要予測期間         | 予測基準日の翌日から14日間 |

想定商品数は利用規模を示すものであり、登録可能な商品の上限を示すものではない。

同時利用者数、販売実績の想定保持期間および性能評価用のデータ規模については、性能・拡張性要件で定義する。

### 4.2 開発および運用の前提

- 個人開発プロジェクトとして開発する。
- ソースコードおよび開発成果物はGitHubで管理する。
- 原則として無料で利用可能なインフラサービスを活用する。
- 公開デモ環境では実際の企業の機密情報や個人情報を使用しない。
- 開発環境と公開環境を区別する。
- インフラサービスの利用制限および運用コストを考慮する。

### 4.3 可用性に関する前提

StockPilotはポートフォリオとしての公開を想定する。

初期リリースでは、商用サービスと同等の稼働保証や24時間365日の運用監視を必須としない。

ただし、障害発生時のデータ保護、復旧手段および利用者への適切な状態表示については、必要な品質要件を定義する。

### 4.4 セキュリティに関する前提

無料公開および個人開発であることを理由として、基本的なセキュリティ対策を省略しない。

認証情報、秘密情報および業務データを適切に保護する。

公開デモ環境については、不正利用、過剰なアクセスおよびデータ破壊への対策を考慮する。

### 4.5 機械学習システムに関する前提

需要予測モデルの精度評価および業務改善効果の検証については、機能要件定義書の分析・評価要件に従う。

本書では、予測処理の性能、再現性、モデルの管理および障害時の取り扱いなど、機械学習システムの品質に関する要件を定義する。

#### 7.2.4 NFR-008：CSV処理性能

| 項目         | 内容                                                           |
| ------------ | -------------------------------------------------------------- |
| 要件ID       | NFR-008                                                        |
| 要件名       | CSV処理性能                                                    |
| 要件分類     | NFC-002                                                        |
| 定義理由     | 販売実績の一括登録を現実的な処理時間で実施できるようにするため |
| 優先度       | Must                                                           |
| 対象リリース | v0.1.0                                                         |

##### 要件内容

販売実績CSVの受付規模および処理時間を以下のとおり定義する。

| 項目                         | 定義値                   |
| ---------------------------- | ------------------------ |
| 最大ファイルサイズ           | 5 MiB（5,242,880バイト） |
| 最大データ行数               | 5,000行                  |
| アップロード後の検証処理時間 | 30秒以内                 |
| 確認後のインポート処理時間   | 30秒以内                 |

- 最大データ行数にはヘッダー行を含めない。
- CSVのデータ行数はCSV形式として解析したレコード数を基準とする。
- ファイルサイズおよびデータ行数の両方の制約を満たす必要がある。
- 通常販売実績および過去販売実績の両方に適用する。
- 上限を超えるファイルは受け付けないこと。
- 上限超過時に業務データを部分的に登録しないこと。
- 検証処理時間はファイル受信完了から検証結果が利用可能となるまでとする。
- インポート処理時間は登録処理の受付から登録結果が利用可能となるまでとする。
- 利用者による確認操作の待ち時間は処理時間に含めない。
- 処理時間の短縮を目的として、業務上必要な検証およびデータ整合性の確保を省略しないこと。

公開デモ環境では、資源保護のために別途利用制限を設けることができる。ただし、通常の受付上限と公開デモ環境の制限を区別して管理する。

##### 受入基準

- ファイルサイズおよび行数の制約を満たす正常な5,000行のCSVを処理できること。
- 基準規模のデータベースに対して、検証およびインポートがそれぞれ30秒以内に完了すること。
- ファイルサイズまたは行数の上限を超える場合に処理が拒否されること。
- 上限超過および処理失敗によって部分的な業務データ登録が発生しないこと。

#### 7.5.7 NFR-025：不正利用および過剰アクセス対策

| 項目         | 内容                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| 要件ID       | NFR-025                                                                  |
| 要件名       | 不正利用および過剰アクセス対策                                           |
| 要件分類     | NFC-005                                                                  |
| 定義理由     | 不正な認証試行および過剰な処理実行によるサービス品質の低下を防止するため |
| 優先度       | Must                                                                     |
| 対象リリース | v0.1.0                                                                   |

##### 要件内容

以下の処理について、必要に応じて実行頻度および同時実行数を制限すること。

- ログイン処理
- 通常のAPIリクエスト
- 業務データの登録および更新処理
- CSVアップロードおよびインポート処理
- 需要予測処理（v1.0.0）

実行制限については、以下の方針を適用する。

- ログイン処理に対する総当たり攻撃を抑制すること。
- 資源消費の大きい処理について、通常のAPI処理とは異なる制限を設定できること。
- 制限の判定には、処理の特性に応じてアカウント、接続元およびその他の適切な識別情報を使用すること。
- 接続元の識別情報を使用する場合は、信頼できない転送ヘッダーによって制限を容易に回避できないようにすること。
- 実行制限を超過したリクエストについて、対象処理を適切に拒否すること。
- 実行頻度の制限によって拒否する場合は、原則としてHTTPステータスコード429を使用すること。
- 再試行可能な時期を提示できる場合は、適切な情報を提供すること。
- 実行制限の超過によって部分的な業務データ更新が発生しないこと。
- 通常の利用者による業務操作を不必要に妨げないこと。

大規模なDDoS攻撃に対する完全な防御を保証するものではない。

#### 7.7.5 NFR-037：アクセシビリティの確保

| 項目         | 内容                                                               |
| ------------ | ------------------------------------------------------------------ |
| 要件ID       | NFR-037                                                            |
| 要件名       | アクセシビリティの確保                                             |
| 要件分類     | NFC-007                                                            |
| 定義理由     | 利用者の操作方法および視認性の違いによる利用上の障壁を抑制するため |
| 優先度       | Must                                                               |
| 対象リリース | v0.1.0                                                             |

##### 要件内容

WCAG 2.2の適合レベルAAに含まれる関連基準を参考として、主要画面のアクセシビリティを確保する。

文字および操作要素のコントラスト比について、以下の基準を適用する。

| 対象                                           | 最小コントラスト比 |
| ---------------------------------------------- | ------------------ |
| 通常サイズの文字                               | 4.5:1              |
| 大きな文字                                     | 3:1                |
| 操作要素および状態の識別に必要な非テキスト情報 | 3:1                |

大きな文字の判定およびコントラスト比の適用除外については、WCAG 2.2の関連基準に従う。

以下の方針を適用する。

- 主要な操作をキーボードによって実行できること。
- キーボード操作時のフォーカス位置を視覚的に確認できること。
- フォーカスの移動順序を操作内容に応じた自然な順序とすること。
- フォーカスが意図せず特定の操作要素に閉じ込められないこと。
- 入力項目と対応するラベルを適切に関連付けること。
- 見出し、一覧表および操作要素に適切なHTMLの意味構造を使用すること。
- アイコンのみの操作要素には、操作内容を識別できるアクセシブルな名前を付与すること。
- 情報を伝える画像には、必要に応じて代替テキストを提供すること。
- エラー、警告および業務状態を色のみで表現しないこと。
- ダイアログを使用する場合は、適切なフォーカス管理を行うこと。
- 文字を200%まで拡大した場合に、主要な情報および操作が不必要に失われないこと。
- 動的に変化する重要な処理結果について、支援技術によって認識できるようにすること。
- v1.0.0では、グラフによって提供する主要な情報を、数値、表または説明文などの代替手段でも確認できるようにすること。

WCAG 2.2 AAへの完全適合および第三者によるアクセシビリティ認証は、初期リリースの必須対象としない。

本要件で明示した基準について確認を行い、未対応事項および改善方針を記録する。

##### 受入基準

- 主要な操作をキーボードのみで実行できること。
- フォーカス位置を視覚的に確認できること。
- 主要な文字および操作要素が定義されたコントラスト比を満たすこと。
- 入力項目および主要な操作要素に適切な名前が設定されていること。
- 重要な業務状態が色のみに依存せず表示されていること。
- 文字の拡大によって主要な情報および操作が失われないこと。
- v1.0.0では、グラフの主要な情報を代替手段によって確認できること。
- アクセシビリティの確認結果および残存する課題が記録されていること。

- キーボードによる操作確認

- アクセシビリティ検査ツールによる確認
- 文字拡大時の表示確認
- 主要画面の支援技術を考慮した手動確認
- グラフおよび代替情報の確認（v1.0.0）

#### 7.9.1 NFR-045：分析・学習データの品質管理

| 項目         | 内容                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| 要件ID       | NFR-045                                                                  |
| 要件名       | 分析・学習データの品質管理                                               |
| 要件分類     | NFC-009                                                                  |
| 定義理由     | 不適切なデータによる分析結果および需要予測結果の信頼性低下を防止するため |
| 優先度       | Must                                                                     |
| 対象リリース | v1.0.0                                                                   |

##### 要件内容

- 分析、モデル学習および評価に使用するデータの取得元を明確にすること。
- データセットの利用条件およびライセンスを確認すること。
- データの対象期間、対象商品、項目定義および集計単位を把握すること。
- データ型、欠損値、重複値、異常値および日付の整合性を確認すること。
- 商品単位および日付単位のデータの一意性を確認すること。
- 販売数量0と販売実績の欠損を区別すること。
- 欠損値を無条件に0として扱わないこと。
- 取消済みの販売実績を有効な販売実績として扱わないこと。
- データの補完、除外および変換を行う場合は、その理由および処理内容を記録すること。
- 異常値を業務上の理由を確認せずに一律に除外しないこと。
- 欠品などによって観測された販売数量が実際の需要を下回る可能性を考慮すること。
- 販売数量を需要の代理指標として使用する場合は、その制約を明示すること。
- 合成データを使用する場合は、実際の観測データと区別すること。
- シミュレーション用の仮定値と、データセットから取得した値を区別すること。
- 学習および推論に使用するデータの形式を検証すること。
- 必要な品質基準を満たさないデータを無条件に学習または推論へ使用しないこと。

具体的なデータセット、欠損値処理、異常値処理および最低データ充足条件は、分析・機械学習設計およびモデル開発工程で決定する。

#### 7.9.3 NFR-047：データリーケージ防止

| 項目         | 内容                                                             |
| ------------ | ---------------------------------------------------------------- |
| 要件ID       | NFR-047                                                          |

| 要件分類     | NFC-009                                                          |

| 優先度       | Must                                                             |

##### 要件内容

- 時系列データの特性を考慮した学習、検証および最終評価データの分割を行うこと。
- 原則として、時系列の順序を無視したランダム分割を使用しないこと。
- 学習処理に検証データおよび最終評価データの正解情報を不適切に混入させないこと。
- モデルの学習、前処理パラメータの算出および特徴量の選択について、利用可能なデータ範囲を明確にすること。

- 販売促進情報などを使用する場合は、予測時点で利用可能な情報であることを確認すること。
- モデル選択およびハイパーパラメータ調整は、原則として学習データおよび検証データを使用して行うこと。
- 最終評価データを用いた結果確認後に、その結果に合わせてモデルを調整し、同じデータを独立した最終評価として扱わないこと。
- 最終評価後に追加のモデル調整を行う場合は、独立した評価データを確保するか、評価上の制約を明示すること。
- ベースラインモデルと提案モデルの比較において、同等の情報利用条件を適用すること。
- 学習時と公開環境における推論時の情報利用条件の差異を確認すること。

過去の販売実績について、後日行われた訂正などの履歴を予測時点の状態として再現できない場合は、その制約を記録すること。

具体的な時系列分割方法、特徴量および複数日先の予測方式は、モデル開発工程で決定する。

##### 受入基準

- 時系列分割の条件が明確になっていること。
- 学習、検証および最終評価データの用途が区別されていること。
- 特徴量生成に予測時点で利用できない情報が含まれていないこと。
- 複数日先の予測に未知の実績値が使用されていないこと。

#### 7.9.5 NFR-049：推論結果の品質および整合性

| 項目         | 内容                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| 要件ID       | NFR-049                                                                        |
| 要件名       | 推論結果の品質および整合性                                                     |
| 要件分類     | NFC-009                                                                        |
| 定義理由     | 不正な需要予測結果が欠品リスク判定および発注判断に使用されることを防止するため |
| 優先度       | Must                                                                           |
| 対象リリース | v1.0.0                                                                         |

##### 要件内容

- 推論処理の実行前に、必要な入力データおよびモデルの利用可否を確認すること。
- 学習時と推論時の前処理および特徴量定義の整合性を確保すること。
- モデルが必要とする入力形式およびデータ型を検証すること。
- 需要予測結果の対象商品、予測基準日および予測対象期間を検証すること。
- 予測基準日の翌日から連続する14日分の需要予測結果が存在することを確認すること。
- 予測対象日の重複および欠落がないことを確認すること。
- 需要予測数量が有限の非負数であることを確認すること。
- NaN、正負の無限大および負の需要予測数量を有効な予測結果として扱わないこと。
- 小数の需要予測数量を、機能要件に反して無条件に整数化しないこと。
- モデルの出力を補正する場合は、補正方法を明確にし、評価時と推論時で整合した処理を行うこと。
- 必要な予測結果が不足している場合は、当該商品の予測を正常完了として扱わないこと。
- 不正な予測結果を有効な予測結果として保存または公開しないこと。
- 予測結果の有効性について、機能要件定義書に従って判定すること。
- 販売実績の変更、予測対象期間の経過およびモデルの変更などによる有効性への影響を適切に管理すること。
- 無効な予測結果を将来在庫、リスク判定および発注提案の根拠として使用しないこと。
- データ不足または推論失敗を、需要予測数量0として扱わないこと。
- 商品単位で予測処理の結果を識別できること。
- 一部の商品で推論処理が失敗した場合は、機能要件に従って他の商品の処理結果を取り扱うこと。

推論結果の主な検証項目を以下に示す。

| 検証項目       | 検証基準                                     |
| -------------- | -------------------------------------------- |
| 対象商品       | 予測対象として有効な商品であること           |
| 予測基準日     | 機能要件で定義された日付であること           |
| 予測対象期間   | 予測基準日の翌日から14日間                   |
| 予測結果件数   | 商品単位で14件                               |
| 予測対象日     | 重複および欠落がないこと                     |
| 予測数量       | 有限の非負数であること                       |
| モデル情報     | 使用したモデルを識別できること               |
| 入力データ情報 | 有効性の判定に必要な情報を確認できること     |
| 処理状態       | 正常完了、予測不可または失敗を区別できること |

予測結果の形式および数値が妥当であることと、予測精度が高いことは区別する。

予測精度についてはAR-005に従って評価する。

##### 受入基準

- 正常な入力データおよびモデルから14日分の予測結果を生成できること。
- 不正な形式および数値の予測結果が検出されること。
- 予測対象日の重複および欠落が検出されること。
- 不正な予測結果が業務判断に使用されないこと。
- 予測不可、推論失敗および正常な需要予測数量0が区別されていること。
- 予測結果の有効性が機能要件に従って管理されていること。
- 商品単位の処理結果が適切に管理されていること。

##### 確認方法

- 予測結果の有効性判定テスト

| 失敗商品数       | 処理上の異常によって予測できなかった商品数   |
| 処理状態         | 需要予測処理の実行状態                       |
| 異常情報         | 原因調査に必要なエラー情報                   |

処理中または処理が中断された場合は、未処理の商品が存在する可能性を考慮すること。

未処理の商品を成功、予測不可または失敗として無条件に集計しないこと。

需要予測の運用状況を確認するため、実行時間、失敗状況およびデータ不足の発生状況を必要に応じて確認できること。

予測精度の低下や入力データの分布変化については、必要な実績データが得られる場合に、後続のモデル評価および更新判断で確認する。

リアルタイムのモデル監視基盤、データドリフトの自動検知、予測精度低下の自動通知および自動再学習は、初期リリースの必須対象としない。

具体的なログ形式、保存期間、確認頻度および異常時の対応手順は、後続の設計工程で決定する。

##### 受入基準

- モデル読み込みおよび推論処理の異常を検知できること。
- データ不足と処理上の異常を区別できること。
- 推論処理の実行状況および処理結果を確認できること。
- 異常発生時に原因調査に必要な情報を確認できること。

- 不正な予測結果が業務判断に使用されないこと。

- 推論処理の例外発生時のテスト
- ログおよび実行記録の確認
- 一部商品での予測失敗を想定したテスト

9. 反映後の動作確認

## 8. 品質評価および確認方針

### 8.1 基本方針

第7章の受入基準を正とし、対象リリースごとにテスト、測定およびレビューによって確認する。要件定義時点の目標値と実測値を区別する。Mustの未達は改善または正式な要件変更によって対応し、Shouldの延期は理由と影響を記録する。

### 8.2 性能評価

NFR-005の基準規模を使用し、NFR-006〜NFR-010に従って評価する。通常API、画面、CSV、需要予測の測定区間を区別する。環境、データ件数、同時利用者数、試行回数、起動状態、成功・失敗件数および測定値を記録する。除外条件は各要件に従い、除外した結果も理由とともに記録する。無料環境の制約により測定できない場合は未測定とし、合格とは扱わない。

### 8.3 セキュリティ評価

NFR-019〜NFR-028を対象とし、未認証アクセス、認証状態の無効化、不正入力、過剰アクセス、秘密情報の露出および公開デモの保護を確認する。依存関係の脆弱性確認と設定レビューを実施する。攻撃を模した試験は許可された隔離環境で行う。

### 8.4 障害対応および復旧確認

NFR-001〜NFR-004、NFR-011〜NFR-018に従い、通信障害、処理中断、再送、競合、バックアップからの復元およびマイグレーションを確認する。復元試験は隔離環境で行い、復旧時間、復元可能時点、業務データの整合性を記録する。

### 8.5 ユーザビリティ評価

NFR-029、NFR-033〜NFR-037に従い、対象ブラウザと画面サイズで主要業務を確認する。入力エラー、処理状態、確認操作、キーボード操作および視認性を確認する。自動検査だけでなく手動確認を併用する。

### 8.6 機械学習システム品質評価

NFR-009、NFR-045〜NFR-051およびAR-001〜AR-007に従い、データ品質、時系列検証、再現性、モデル識別、推論結果、異常時の処理および更新・切り戻しを確認する。予測精度と業務改善効果の評価は機能要件定義書に従う。KPIの目標達成と評価作業の完了を区別する。

### 8.7 評価結果の記録

評価記録には要件ID、確認日、対象バージョン、環境、手順、期待結果、実測結果、判定（合格・不合格・未実施・対象外）、証跡および課題を記載する。対象外には理由を付す。未実施を合格として扱わない。詳細なテストケースと証跡の保存先は後続工程で定義する。

### 11.4 後続工程への引き継ぎ

未決事項は、決定理由、決定内容、関連要件および影響範囲を記録し、必要な設計・テスト成果物へ反映する。要件自体を変更する場合は第3.7節に従う。未決事項を残したまま対象リリースの受入基準を満たしたとは判断しない。
