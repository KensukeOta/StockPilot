## 2. プロジェクト概要

### 2.1 プロジェクト名称

- 名称：StockPilot
- 英語名称：Demand Forecasting & Inventory Management System
- 日本語名称：需要予測・在庫管理システム

### 2.2 プロジェクトの背景

小売業における在庫管理では、商品の欠品や過剰在庫、発注業務の属人化などが課題となる場合がある。

特に、表計算ソフトを中心とした手作業による在庫管理では、データの更新漏れや入力ミス、集計業務の負担が発生する可能性がある。

また、担当者の経験や勘に依存した発注業務では、需要の変動や季節性を十分に考慮できず、適切な在庫水準を維持することが難しい場合がある。

本プロジェクトでは、これらの課題を抱える架空の小売企業を想定し、Webシステムとデータ分析・機械学習を活用した解決策を検討する。

### 2.3 プロダクトコンセプト

**経験や勘に頼った在庫管理から、データに基づく在庫管理へ。**

StockPilotは、商品・売上・在庫情報を一元管理し、需要予測と発注数量の提案を通じて、小売企業の在庫管理業務および意思決定を支援するWebシステムである。

### 2.4 プロジェクトの目的

- 商品・売上・在庫情報の一元管理
- 在庫管理業務の効率化
- 商品の欠品および過剰在庫の抑制
- 発注業務の属人化の軽減
- データに基づく意思決定の支援
- 機械学習を活用した需要予測の実用性の検証

## 4. 現状の業務分析（As-Is）

### 4.1 現状の業務フロー

1. 店舗で商品を販売する。
2. 販売実績をExcelに転記する。
3. Excel上の在庫数と実際の在庫数を照合する。
4. 担当者の経験や勘に基づいて発注数量を決定する。
5. 仕入先へ商品を発注する。
6. 商品の入荷後、Excel上の在庫情報を更新する。

### 4.2 ビジネス課題

| ID     | 課題             | 想定される原因    | ビジネスへの影響     |
| ------ | ---------------- | ----------------- | -------------------- |
| BP-001 | 商品の欠品       | 需要の把握不足    | 販売機会の損失       |
| BP-002 | 過剰在庫         | 必要以上の発注    | 在庫保管コストの増加 |
| BP-003 | 在庫数の不一致   | 手入力・更新漏れ  | 在庫情報の信頼性低下 |
| BP-004 | 発注業務の属人化 | 経験や勘への依存  | 判断のばらつき       |
| BP-005 | 集計業務の負担   | Excelによる手作業 | 業務効率の低下       |

### 4.3 課題の根本原因

現状の課題は、主に以下の3つに分類できる。

**データ管理**

- 情報が複数のファイルに分散している。
- 手作業によるデータ入力が多い。
- 在庫情報の更新漏れが発生する可能性がある。

**需要予測**

- 将来の需要を定量的に予測する仕組みがない。
- 季節性や曜日による需要変動を十分に考慮できていない。

**業務プロセス**

- 発注数量の判断が担当者の経験に依存している。
- 発注判断の基準が標準化されていない。
- 集計や確認作業に時間を要している。

## 5. 解決方針（To-Be）

### 5.1 システムによる解決策

| 課題ID | 解決策                                                                   |
| ------ | ------------------------------------------------------------------------ |
| BP-001 | 需要予測、将来在庫推移の推定、欠品リスクの可視化および入荷予定管理       |
| BP-002 | 現在庫、需要予測、発注条件および入荷予定に基づく発注数量の提案           |
| BP-003 | 在庫情報の一元管理、入出庫履歴の記録、入力検証および業務データの訂正処理 |
| BP-004 | データに基づく発注数量の提案および発注判断の根拠の可視化                 |
| BP-005 | CSVインポート、ダッシュボードおよび売上分析による集計業務の効率化        |

### 5.2 システム導入後の業務フロー

#### 5.2.1 初期導入時の業務フロー

1. システム運用担当者が利用アカウントを準備する。
2. 店舗の在庫管理開始日を設定する。
3. カテゴリおよび商品情報を登録する。
4. 商品ごとの在庫管理開始日および初期在庫を登録する。
5. 必要に応じて過去の販売実績をCSVファイルから取り込む。
6. 登録された商品、販売実績および在庫情報を確認する。

過去の販売実績は、売上分析および需要予測に利用するためのデータとして登録する。

過去の販売実績の登録によって現在庫数量を変更しない。

#### 5.2.2 日常業務のフロー

1. 店舗で商品を販売する。
2. 通常の販売実績をCSVファイルから取り込む。
3. 販売実績に基づいて現在庫数量を更新する。
4. ダッシュボードおよび売上分析によって業務状況を確認する。
5. 過去の販売実績から将来の需要を予測する。
6. 需要予測、現在庫、調達リードタイム、安全在庫および入荷予定などに基づいて将来在庫推移と欠品リスクを確認する。
7. システムが推奨発注数量および算出根拠を提示する。
8. 担当者が提案内容を確認し、最終的な発注数量を決定する。
9. 担当者がシステム外で仕入先へ発注する。
10. 発注済み商品の入荷予定を登録する。
11. 商品の入荷後、入荷実績を登録する。
12. 現在庫数量および関連する入荷予定の数量・状態を更新する。

必要に応じて棚卸差異などの在庫調整を行う。

販売実績および入荷実績に入力誤りが判明した場合は、定義された訂正処理によって対応する。

需要予測および発注判断支援に関する業務は、v1.0.0での実現を対象とする。

### 5.3 As-IsとTo-Beの比較

| 業務         | As-Is                       | To-Be                                        |
| ------------ | --------------------------- | -------------------------------------------- |
| 初期導入     | Excelファイルによる個別管理 | 商品情報・初期在庫・過去販売実績の一元登録   |
| 売上管理     | Excelへの手入力             | CSV一括登録                                  |
| 在庫管理     | Excelによる個別管理         | データベースによる一元管理                   |
| 売上分析     | 手作業による集計            | ダッシュボードおよび売上分析による可視化     |
| 需要予測     | 担当者の経験                | 時系列データによる予測                       |
| 発注判断     | 経験や勘                    | データに基づく発注提案および算出根拠の確認   |
| 入荷予定管理 | Excelなどによる個別管理     | 入荷予定・入荷済み数量・未入荷数量の一元管理 |
| 入出庫管理   | Excelによる管理             | 入出庫履歴の記録                             |
| データ訂正   | Excel上の値を直接修正       | 元の記録および訂正履歴を保持した訂正処理     |

### 5.4 意思決定支援の方針

本システムは、発注業務の完全自動化を目的としない。

システムが需要予測および発注数量の提案を行い、最終的な発注判断は担当者が行う。

予測結果には不確実性が存在するため、人による確認を前提とした意思決定支援システムとして設計する。

需要予測に必要なデータが不足している場合や、有効な予測結果が存在しない場合は、その状態を利用者に明示する。

必要な判断材料が不足している場合は、根拠のない発注数量を提示しない。

入荷予定は将来の入荷を保証するものではないため、入荷遅延などの不確実性を考慮する。

仕入先への実際の発注はシステム外で行い、StockPilotは発注判断および発注後の入荷予定管理を支援する。

## 6. プロジェクトの評価指標（KPI）

### 6.1 目標値

| ID      | 評価指標            | 目標値                              |
| ------- | ------------------- | ----------------------------------- |
| KPI-001 | 欠品率              | 従来方式と比較して20%削減           |
| KPI-002 | 平均在庫金額        | 従来方式と比較して15%削減           |
| KPI-003 | 発注作業時間        | 従来方式と比較して50%削減           |
| KPI-004 | 需要予測誤差（MAE） | ベースラインモデルと比較して10%改善 |

上記の数値は企画段階における暫定的な目標値であり、実際の改善実績を示すものではない。

### 6.2 検証方法

| KPI     | 検証方法                                       |
| ------- | ---------------------------------------------- |
| KPI-001 | 在庫・発注シミュレーションによる欠品率の比較   |
| KPI-002 | 同一条件下での平均在庫金額の比較               |
| KPI-003 | 模擬業務における発注作業時間の測定             |
| KPI-004 | 時系列を考慮した検証データによる予測精度の比較 |

評価指標の具体的な計算方法、比較対象、検証条件については、後続工程で定義する。

実際の企業への導入は行わないため、公開データまたは合成データを用いて検証する。

### 6.3 KPIの評価および達成判定方針

KPIは、本システムの需要予測精度および業務改善効果を評価するための指標とする。

評価においては、比較対象間の条件を可能な限り統一し、評価方法および使用したデータを記録する。

需要予測精度の評価では、時系列データの特性を考慮し、将来の情報が学習時に混入しないようにする。

業務改善効果の評価では、シミュレーションまたは模擬業務による結果と、実際の企業への導入による効果を区別する。

各KPIについて、目標値、評価結果、達成状況および考察を記録する。

KPIの目標達成状況と、システムおよび分析・評価成果物の完成判定は区別する。

KPIが目標値に達しなかった場合も、評価結果、未達成の要因、評価上の制約および今後の改善方針を記録する。

KPIの未達成のみを理由として、プロジェクト全体を未完成とは判定しない。

具体的な評価方法および完了判定は、機能要件定義書ならびに後続工程で定義する。

## 7. プロジェクトスコープ

### 7.1 v0.1.0：業務システム基盤

商品、販売実績および在庫情報を一元管理するための業務システム基盤を構築する。

主な対象機能は以下のとおりとする。

- ログイン・認証
- システム初期設定
- カテゴリ管理
- 商品マスタ管理
- 現在庫管理
- 初期在庫登録
- 入荷実績登録
- 在庫調整
- 入出庫履歴管理
- 販売実績管理
- 販売実績および入荷実績の訂正
- 販売実績CSVテンプレートの取得
- 販売実績CSVの検証および登録内容の確認
- 通常販売実績のCSVインポート
- 過去販売実績のCSVインポート
- CSVインポート履歴の確認
- 基本ダッシュボード

また、入力検証、データ整合性維持、二重登録防止、同時操作時の整合性維持およびエラー処理などの共通機能を整備する。

v0.1.0では、基本的な在庫管理業務をStockPilot上で実施できる状態を実現するとともに、需要予測および発注判断支援に必要な業務データの管理基盤を整備する。

### 7.2 v1.0.0：ポートフォリオ完成版

v0.1.0の機能を基盤として、以下の機能を追加または拡張する。

- 売上データ分析

- 将来在庫推移の推定
- 欠品リスクの判定および可視化
- 推奨発注数量の算出
- 発注提案の根拠の表示
- 発注提案ができない場合の案内
- 入荷予定管理
- 入荷予定と入荷実績の連携
- 部分入荷および入荷遅延への対応

また、以下の分析・評価成果物を整備する。

- データ準備および品質確認
- 探索的データ分析
- ベースラインモデルの構築
- 提案モデルの構築

分析・評価処理については、すべてを利用者向けWeb機能として実装することを必須としない。

ポートフォリオとしての完成に向けて、以下も整備する。

- 自動テスト
- CI/CD
- デプロイおよびデモ環境

自動テスト、CI/CDおよびドキュメントの整備は、v1.0.0の開発時に初めて実施するものではなく、開発全体を通じて継続的に行う。

各機能の優先度、詳細な対象範囲およびリリース完了条件は、機能要件定義書に従う。

## 10. プロジェクトの制約・前提条件

### 10.1 制約条件

- 個人開発として実施する。
- 開発費用は原則として無料の範囲に収める。
- 初期リリースでは単一店舗を対象とする。
- 実際の企業システムとの連携は行わない。
- 実在する企業の機密情報や個人情報は使用しない。
- 外部データを使用する場合は利用規約およびライセンスを確認する。

### 10.2 前提条件

- 想定顧客企業および業務課題は架空の設定である。
- 売上データには公開データまたは合成データを使用する。
- 業務改善効果はシミュレーションまたは模擬業務によって評価する。
- 最終的な発注判断は担当者が行う。
- 仕入先への実際の発注はシステム外で行う。
- 利用者はシステム運用担当者が事前に準備したアカウントを使用する。
- 販売実績および入荷実績は、定義された業務ルールに従って登録する。
- 在庫管理および発注判断支援は、システムに登録された業務データに基づいて行う。

### 10.3 業務上の前提

| 項目                 | 前提                       |
| -------------------- | -------------------------- |
| 対象店舗数           | 1店舗                      |
| 想定商品数           | 約500商品                  |
| 表示言語             | 日本語                     |
| 通貨                 | 日本円（JPY）              |
| 業務上のタイムゾーン | Asia/Tokyo                 |
| 商品数量の単位       | 個                         |
| 在庫数量             | 0以上の整数                |
| 販売実績の集計単位   | 商品別・日別               |
| 需要予測の単位       | 商品別・日別               |
| 需要予測期間         | 予測基準日の翌日から14日間 |
| 調達リードタイム     | 商品ごとに1〜7日           |
| 発注間隔             | 原則1日                    |
| 安全在庫             | 商品ごとに設定             |
| 入荷予定の管理単位   | 商品別・入荷予定単位       |

想定商品数は利用規模の目安であり、登録可能な商品の上限を示すものではない。

店舗全体の在庫管理開始日と、商品単位の在庫管理開始日を区別する。

通常販売実績と過去販売実績は、商品単位の在庫管理開始日を基準として区分する。

通常販売実績は現在庫数量に反映し、過去販売実績は現在庫数量に反映しない。

具体的な業務ルール、入力制約および例外処理は、業務要件定義書および機能要件定義書に従う。

性能目標、データ容量の上限および運用上の制約は、非機能要件定義で具体化する。

## 11. リスクと対応方針

| ID    | リスク                                               | 対応方針                                                                                       |
| ----- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| R-001 | 十分な売上データを確保できない                       | 公開データや合成データの利用を検討し、データの充足性および品質を確認する                       |
| R-002 | 需要予測の精度が目標に達しない                       | ベースラインとの比較、誤差分析および未達成要因の記録を行う                                     |
| R-003 | 開発規模が過大になる                                 | MVPを定義し、要件の優先度に基づいて段階的に機能を追加する                                      |
| R-004 | 在庫情報に不整合が発生する                           | トランザクション管理、入力検証、二重登録防止、同時操作時の整合性維持および訂正履歴の管理を行う |
| R-005 | 無料インフラの制約を超過する                         | リソース使用量を確認し、構成を見直す                                                           |
| R-006 | 予測結果に過度に依存する                             | 予測の限界および有効性を明示し、担当者による判断を前提とする                                   |
| R-007 | 欠品時の売上を実際の需要と誤認する                   | 欠品による販売機会の損失を考慮し、データの限界を明示する                                       |
| R-008 | 入荷予定どおりに商品が入荷しない                     | 未入荷数量および入荷遅延を把握し、遅延した入荷予定を確実な将来入荷として扱わない               |
| R-009 | 販売実績の追加や訂正によって既存の予測結果が古くなる | 予測結果の有効性を判定し、必要に応じて再予測を案内する                                         |
| R-010 | 公開デモ環境で意図しない操作や過剰な利用が発生する   | 認証、利用制限、デモデータの管理および運用上の対策を検討する                                   |

## 12. プロジェクトの成功条件

本プロジェクトでは、以下の条件を満たすことを成功条件とする。

### 12.1 業務システムとしての成功条件

- 商品・販売実績・在庫情報を一元管理できること。
- 通常販売実績および過去販売実績をCSVで取り込めること。
- 現在庫数量および入出庫履歴の整合性を維持できること。
- 販売実績および入荷実績の入力誤りに対して、定義された訂正処理を行えること。
- ダッシュボードおよび売上分析によって売上・在庫状況を確認できること。
- 過去の販売実績から商品別・日別の需要を予測できること。
- 将来在庫推移および欠品リスクを確認できること。
- 需要予測および関連する業務データに基づいて発注数量を提案できること。
- 発注提案の算出根拠を確認できること。
- 入荷予定を管理し、入荷実績との整合性を維持できること。

### 12.2 分析・評価に関する成功条件

- ベースラインモデルおよび提案モデルを構築できていること。
- 適切な検証方法によって需要予測精度を評価できていること。
- シミュレーションまたは模擬業務によって業務改善効果を評価できていること。
- KPI-001〜KPI-004の評価結果および達成状況が記録されていること。
- 分析結果、評価上の制約および今後の改善方針が記録されていること。
- 機能要件定義書で定義した分析・評価成果物が整備されていること。

KPIの目標達成状況と、分析・評価成果物の完成判定は区別する。

### 12.3 品質・ポートフォリオとしての成功条件

- v1.0.0までのすべてのMust要件を満たしていること。
- 対象となる非機能要件を満たしていること。
- 必要な自動テストおよび品質確認が完了していること。
- 第三者が定められた利用方法に従ってデモアプリを利用できること。
- 設計・開発・テスト・運用に関する成果物がGitHubに掲載されていること。
- システムの利用方法および実行方法が記録されていること。
- 技術選定、設計判断および予測モデルの採用理由を説明できること。

具体的なリリース完了条件は、機能要件定義書、非機能要件定義書および後続の設計・テスト工程で定義する。

## 13. 期待される効果

本システムの導入により、以下の効果が期待される。

- 在庫管理業務の効率化
- 販売機会の損失の抑制
- 過剰在庫の削減
- 発注業務の標準化
- データに基づく意思決定の促進

これらの効果については、開発後の検証を通じて評価する。
